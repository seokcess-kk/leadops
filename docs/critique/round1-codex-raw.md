1. [SEVERITY: BLOCKER] 정보통신망법 제50조의2의 법적 전제를 약 20년 전 문언으로 잘못 잡아, “무단수집 거부” 문구가 없는 홈페이지에서는 자동 수집해도 된다는 위험한 설계를 만들었다. 현행 조문은 거부 문구 유무가 아니라 홈페이지 운영자·관리자의 사전 동의 없이 자동으로 이메일 주소를 수집하는 행위 자체를 금지한다. 따라서 문구 탐지 하드 게이트는 과잉이 아니라 심각하게 과소포괄적이며, 이메일을 먼저 추출한 뒤 문구를 발견해 폐기하는 방식도 위반을 되돌리지 못한다. [현행 제50조의2 문언](https://www.law.go.kr/LSW/lsInfoP.do?lsiSeq=116791)을 기준으로 자동 홈페이지 이메일 수집을 중단하고, 운영자 동의가 확인된 사이트·공공 API의 명시적 연락처·사람이 직접 확인한 연락처처럼 별도 근거가 있는 경로만 허용하도록 법률 검토 후 재설계해야 한다.

2. [SEVERITY: BLOCKER] 네이버 검색 API를 아웃바운드 리드 생성에 쓰는 것 자체가 네이버 API 약관의 금지 목적에 걸릴 가능성이 매우 높다. 약관 7.3②는 API를 “스팸/광고 정보의 작성 및 전송을 위하여” 이용하는 행위를 금지하며, 이 제품은 이름부터 승인 리드를 영업에 쓰기 위한 시스템이다. 또한 검색 결과를 점수로 변형하고 일부만 보여주는 대시보드는 검색 결과의 독립 노출·비왜곡을 요구하는 검색 API 특약 2.1과도 충돌할 수 있어, 문서가 말하는 “내부 분석·원문 최소 저장”은 해결책이 아니다. [네이버 API 이용약관](https://developers.naver.com/products/terms/)에 대한 네이버의 서면 사용승인을 받기 전에는 핵심 데이터원으로 확정하지 말고, 승인 실패 시 네이버 지표 없이도 성립하는 제품으로 요구사항을 다시 잡아야 한다.

3. [SEVERITY: BLOCKER] Google Custom Search JSON API 비용 가정은 2026년 7월 현재 신규 프로젝트라면 실행 불가능하다. 이 API는 신규 고객에게 닫혔고 기존 고객도 2027년 1월 1일 종료 예정이므로, “100쿼리/일 무료”는 기존 계정에만 잠시 유효한 레거시 조건이다. 홈페이지 발견·구글 보완 검증에 이 API를 넣은 순간 신규 MVP의 공급원이 존재하지 않는다. [Google 공식 종료 안내](https://developers.google.com/custom-search/v1/overview)를 반영해 CSE를 제거하고, 공공데이터의 홈페이지 필드·사업자 제공 URL·수동 검색 등 합법적 대체 경로의 수율과 비용을 Phase 0 전에 다시 산정해야 한다.

4. [SEVERITY: BLOCKER] SoSR은 “네이버 체감 노출”의 프록시라기보다 서로 다른 다섯 API 검색공간에서의 문서 회수율을 임의로 합산한 별개 지표다. 통합검색은 모듈 선택·광고·플레이스·개인화·지역·기기·시점에 따라 구성되지만 API는 blog/cafe/web/news/local별 독립 정렬이며, local은 최대 5건인데 다른 채널은 최대 100건이라 분모조차 호환되지 않는다. 동일 URL 중복, 채널별 발행량 차이, 날짜가 없는 web/local 결과, 브랜드 키워드와 비브랜드 키워드의 전혀 다른 의미 때문에 높은 SoSR이 실제 사용자 노출을 의미하지 않는다. 지표 이름을 “Open API 콘텐츠 회수 점유율”로 제한하고, SERP 노출·순위·검색점유라는 표현과 35점 핵심 배점을 제거한 뒤 실제 매출/상담 성과와 별도 검증해야 한다.

5. [SEVERITY: BLOCKER] 제시한 수율 산술은 일 50건 목표를 지지하지 않고 오히려 불가능함을 보여준다. 문서의 고정 경로인 기본통과 175건을 적용하면 하한은 `175×0.70×0.25×0.90×0.40=11.0`, 상한은 `175×0.80×0.40×0.90×0.60=30.2`건이지 15~35건이 아니다. 기본통과를 최대 200건으로 올려도 낙관 상한이 34.6건이고, 50건을 내려면 현재 가정에서 기본통과 약 289~794건/일이 필요하다. 50건을 계약 목표에서 제거하거나 이메일·홈페이지 하드 게이트를 합법적으로 바꾸고, 단계별 실측 신뢰구간으로 역산한 처리량을 새 SLA로 확정해야 한다.

6. [SEVERITY: BLOCKER] 신규 후보 400건/일 모델은 유한 모집단을 빠르게 소진하며 문서에는 재검색 전략조차 없다. 실제 원시 적격 모집단이 `U`개라면 신규만 처리할 때 소진일은 단순히 `U/400` 영업일이며, 2만 개면 50일, 3만 개면 75일뿐이다. 이후에는 같은 업체를 반복 분석하거나 신규 개·폐업분만 남으므로 일 15~35건조차 지속할 수 없고, `leads.company_id UNIQUE`는 과거 승인 업체의 재진입까지 영구 차단한다. Phase 0에서 HIRA·공정위 전수로 `U`를 산출하고, `company_observations`, `last_scanned_at`, 변경탐지, 90/180일 cooldown, suppression, 재접촉 자격 및 일일 “신규/재평가” 목표를 따로 설계해야 한다.

7. [SEVERITY: HIGH] 아웃바운드 이메일 발송을 범위 밖으로 선언했지만, 승인·export 단계에서 실제로 가장 중요한 광고성 정보 전송 규제를 통째로 누락했다. 정보통신망법 제50조는 광고성 정보에 명시적 사전 동의를 원칙으로 하고 기존 거래관계 예외도 제한적으로 해석되므로, 공개된 업무용 이메일이라는 사실이 콜드 마케팅 수신동의를 뜻하지 않는다. 수집만 합법화해도 export된 리스트의 사용이 불법이면 제품의 사업 목적은 달성되지 않는다. [법제처 해석례](https://www.law.go.kr/expcInfoP.do?expcSeq=338973)를 기준으로 `consent_basis`, `consent_at`, `source`, `do_not_contact`, `opt_out_at`을 필수화하고, 적법 근거가 없는 리드는 영업 발송용 export에서 제외해야 한다.

8. [SEVERITY: HIGH] 개인정보보호법 대응을 “무료메일·이름형 로컬파트 차단”으로 대체한 것은 법적 근거도 정확도도 없다. `kim@clinic.co.kr` 같은 식별 가능한 직원 주소는 개인정보일 수 있고, `info@naver.com`은 실제 사업 대표 주소일 수 있어 문자열 규칙은 개인정보 여부를 판단하지 못한다. 수집 법적 근거, 목적 제한, 보유기간, 출처·처리목적 고지 요구 대응, 열람·삭제·처리정지, 파기 및 접근기록이 설계에 없다. [개인정보보호법 제20조](https://law.go.kr/LSW/lsLinkCommonInfo.do?lsJoLnkSeq=1020399343)에 맞춰 데이터 항목별 개인정보 판정과 처리근거를 기록하고, 최소수집·보유기간·권리요청·삭제 워크플로를 구현해야 한다.

9. [SEVERITY: HIGH] Hetzner·Supabase·Anthropic 사용은 개인 이메일이나 담당자 이름이 해외로 이동할 수 있는데 국외이전 검토가 전혀 없다. 워커 로그, 오류 추적, LLM 입력, 백업에 회사명과 개인 식별 이메일이 들어가면 처리위탁·보관도 국외이전에 해당할 수 있다. 단순히 “LLM은 점수에 사용하지 않는다”는 조치는 전송 자체의 적법성과 무관하다. [개인정보보호법 제28조의8](https://www.law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1029334953)에 따라 리전·수탁자·이전 항목·보유기간을 확정하고, 이메일과 담당자 정보는 해외 LLM·로그에 절대 보내지 않는 기술적 차단을 둬야 한다.

10. [SEVERITY: HIGH] 네이버 일 호출량 3,200회는 문서 내부의 “5종 API” 설명과 모순된다. 다섯 엔드포인트를 그대로 적용하면 기본 분석 `100×3×5=1,500`, 추가 분석 `30×5×5=750`, 경쟁사 `100×3×1×5=1,500`, 채널 200으로 최소 3,950회다. 경쟁사 SoSR을 본 업체와 같은 3개 키워드로 비교해야 한다면 경쟁사만 4,500회가 되어 합계가 약 6,950회이며, 재시도·백필·수동 재실행은 별도다. 공급자·엔드포인트·키워드·페이지별 호출 그래프를 만들고 캐시 적중률과 재시도 상한을 포함한 최악조건 예산으로 다시 계산해야 한다.

11. [SEVERITY: HIGH] 500MB Supabase Free에 `search_results` 90일 원문성 레코드를 보관하는 것은 몇 주 안에 용량 한도를 넘길 가능성이 높다. 최소 3,950호출에서 호출당 10건만 저장해도 하루 39,500행, 90일 355만 행이며 URL·제목·인덱스를 포함하면 500MB를 쉽게 초과한다. 6,950호출 시 625만 행이고, `http_cache`의 4KB 발췌·JSONB 스냅샷·audit/jobs까지 더해지며 Free는 500MB 초과 시 read-only가 된다. [Supabase 용량 동작](https://supabase.com/docs/guides/platform/database-size)을 기준으로 호출당 저장량까지 바이트 단위로 모델링하고, 집계값만 DB에 두거나 7~14일 원본 보존·객체 저장소·초기 self-host Postgres 중 하나를 선택해야 한다.

12. [SEVERITY: HIGH] `review_decide` 정책의 `WITH CHECK (true)`는 RPC를 강제하기는커녕 일반 사용자가 승인 제한을 직접 우회하도록 허용한다. `status='pending'`인 행이면 인증 사용자는 `status`, `company_id`, `score_id`, `run_id`, `rank`, `decided_by`, `note` 등 모든 열을 임의 변경하고 50건 상한·업종비율 검사를 건너뛸 수 있다. UI가 RPC만 호출한다는 약속은 PostgREST 직접 호출자를 막지 못한다. `review_items`에 대한 authenticated `UPDATE` 권한과 정책을 제거하고, 고정 `search_path`, 호출자 검증, 행 잠금이 있는 `SECURITY DEFINER` RPC에만 `EXECUTE`를 부여해야 한다.

13. [SEVERITY: HIGH] 제안된 `SECURITY DEFINER` RPC는 동시 승인 시 상한을 초과하는 경쟁조건과 기본 공개 실행권 문제를 해결하지 않는다. 두 요청이 동시에 승인 49건을 읽으면 둘 다 통과해 51건이 될 수 있고, PostgreSQL 함수는 별도 `REVOKE`가 없으면 `PUBLIC` 실행 가능성이 있다. `is_admin()`도 객체를 완전 수식하지 않았고 함수 소유자·권한 모델이 정의되지 않았다. 날짜별 승인 카운터 행을 `FOR UPDATE`하거나 advisory lock으로 직렬화하고, `REVOKE EXECUTE FROM PUBLIC` 후 authenticated에만 부여하며 모든 객체를 스키마 수식해야 한다.

14. [SEVERITY: HIGH] 워커가 `service_role`로 “표준 SQL”에 접속한다는 설명은 Supabase의 인증 모델을 혼동하고 있다. `service_role` 키는 PostgREST 계층에서 RLS를 우회하는 JWT 키이지 `postgres.js` 연결용 DB 비밀번호가 아니며, 직접 SQL은 보통 더 강한 DB 역할을 사용하게 된다. 그 자격증명이 탈취되면 이메일·인증·설정·감사로그 전체가 노출 또는 삭제된다. 워커 전용 최소권한 DB 역할과 스테이지별 함수/API를 만들고, 브라우저·Next.js·워커 자격증명을 분리해 회전 절차까지 명시해야 한다.

15. [SEVERITY: HIGH] 큐의 10분 reaper는 느린 정상 잡을 중복 실행시키는 lease 경쟁조건을 갖고 있다. 첫 워커가 계속 실행 중인데 `locked_at`만 오래됐다는 이유로 재큐잉되면 두 번째 워커가 같은 잡을 처리하고, 첫 워커가 뒤늦게 결과와 상태를 덮어쓸 수 있다. `SKIP LOCKED` 자체는 적절하지만 선택과 `running` 전환을 한 트랜잭션의 원자적 `UPDATE … RETURNING`으로 하지 않으면 그 전에도 중복 획득이 가능하다. heartbeat, `lease_expires_at`, 증가하는 fencing token을 추가하고 모든 완료 업데이트에 현재 token 조건을 걸어야 한다.

16. [SEVERITY: HIGH] “각 스테이지는 멱등”이라는 선언과 달리 결과 테이블에 멱등 제약이 빠져 있다. `search_results`에는 `(run_id, company_id, keyword, provider, rank/url)` 유일성이 없고, `cost_ledger`와 `outbox`에는 이벤트 키가 없어 재시도 때 결과·비용·승인 이벤트가 중복된다. `emails UNIQUE(company_id,address)`는 중복을 막지만 여러 발견 URL의 provenance를 잃는 잘못된 방식이다. 스테이지별 입력 버전과 결과 유일키를 실제 DDL로 강제하고, 이메일 본체와 `email_occurrences`, outbox 이벤트와 delivery attempt를 분리해야 한다.

17. [SEVERITY: HIGH] run·stage의 `partial` 전파 규칙은 상태도만 있고 실행 가능한 알고리즘이 없다. 상류 잡이 dead일 때 어떤 하류 잡을 skip하고 어떤 잡을 계속 생성하는지, retry가 이미 생성된 점수·추천·review item을 무효화하는지, stage 카운터를 경쟁 없이 갱신하는지가 정의되지 않았다. 특정 스테이지부터 같은 run을 재실행하면 기존 결과와 승인 후보가 서로 다른 입력 버전을 참조할 수 있다. 명시적 DAG, 입력 completeness 조건, terminal 상태 집계 SQL, 새 attempt/version 단위 및 다운스트림 invalidation 규칙을 정의해야 한다.

18. [SEVERITY: HIGH] ERD에는 실제로 삭제·재실행을 막거나 잘못된 관계를 허용하는 무결성 결함이 다수 있다. `runs UNIQUE(run_date,trigger,created_at)`은 `created_at` 때문에 중복 cron을 전혀 막지 못하고, `review_items.score_id`는 run/company 일치를 보장하지 않으며 cascade도 없어 run 삭제와 충돌할 수 있다. `competitors`는 같은 경쟁사를 여러 rank에 넣을 수 있고 `websites`는 URL 변형마다 중복되며 `first_seen_run/last_seen_run`에는 FK가 없다. cron용 부분 유일 인덱스, 복합 FK, canonical URL/domain, `(run_id,company_id,competitor_company_id)` 유일성 및 명시적 삭제정책을 추가해야 한다.
