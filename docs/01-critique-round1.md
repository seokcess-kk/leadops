## A. 전면 수용 — 1차 출처로 검증한 BLOCKER

### F-01 · 정보통신망법 제50조의2 조문을 잘못 인용했다 (BLOCKER · **검증 완료 · v1이 틀림**)

**v1의 서술 (틀림)**
> "수집을 거부하는 의사가 명시된 인터넷 홈페이지에서 … 수집하여서는 아니 된다" → 거부 문구가 없으면 자동 수집 가능하다고 전제.

**실제 현행 조문 (확인)**
> **제50조의2 제1항** "누구든지 인터넷 홈페이지 운영자 또는 관리자의 **사전 동의 없이** 인터넷 홈페이지에서 자동으로 전자우편주소를 수집하는 프로그램 그 밖의 기술적 장치를 이용하여 전자우편주소를 수집하여서는 아니 된다."
> **제2항** 위반하여 수집된 전자우편주소의 판매·유통 금지
> **제3항** 위 금지 대상임을 알고 정보전송에 이용하는 행위 금지
> **벌칙(제74조)** 1년 이하의 징역 또는 1천만원 이하의 벌금

v1이 인용한 "거부 의사가 명시된" 문언은 **2002년 신설 당시의 입법 취지 설명문**이며, 국내 수천 개 사이트의 "이메일무단수집거부" 안내 페이지에 그대로 복사되어 퍼져 있습니다. 현행 조문의 요건이 아닙니다.

**영향 — 제품 구조가 바뀐다**

거부 문구 탐지 게이트는 **과잉이 아니라 심각하게 과소포괄**이었습니다. 요건이 "운영자의 사전 동의"인 이상, 콜드 리드 발굴에서 홈페이지 운영자의 사전 동의를 받는 것은 정의상 불가능하므로 **홈페이지에서 프로그램으로 이메일을 추출하는 기능 자체를 제거**해야 합니다. 추출 후 폐기하는 방식도 위반을 되돌리지 못한다는 codex의 지적이 맞습니다.

**반영 (v2)**

| v1 | v2 |
|---|---|
| 워커가 홈페이지 HTML에서 정규식으로 이메일 추출 → `emails` 저장 | **삭제.** 워커는 이메일 문자열을 추출·저장하지 않는다 |
| 이메일이 스테이지 6~7의 사전 하드 게이트 | **검수자가 승인 시점에 수동 입력**하는 후행 단계로 이동 |
| — | 워커는 `contact_pages`(연락처가 있을 만한 페이지 URL)만 저장. 이메일 문자열은 저장하지 않음 |
| — | 검수 화면에서 검수자가 해당 URL을 직접 열어 확인 후 **수동 입력** → 그 후 문법·DNS·MX 검증 |
| — | 공공데이터 API가 이메일 필드를 제공하는 경우는 홈페이지 자동수집이 아니므로 사용 가능. `emails.acquisition_method = 'public_api' \| 'manual_entry'` 로 출처 구분 필수 |
| — | **Phase -1에 변호사 법률 검토를 필수 게이트로 추가** |

> 이 문서는 법률 자문이 아닙니다. 위 재설계는 리스크를 낮추는 방향이지만, 실제 운영 전 **국내 IT·개인정보 전문 변호사 검토가 필수**입니다.

### F-03 · Google Custom Search JSON API는 신규 사용 불가 (BLOCKER · **검증 완료**)

Google 공식 문서 확인: *"The Custom Search JSON API is closed to new customers. Existing Custom Search JSON API customers have until **January 1, 2027** to transition to an alternative solution."*

v1의 "무료 100쿼리/일" 가정은 신규 프로젝트에 적용되지 않습니다.

**반영:** 구글 보완 검증을 **MVP 범위에서 제외**합니다. 대체 API를 억지로 끼워 넣지 않고(대부분 유료·약관 미확인), 네이버 단일 소스 + 그 한계를 명시하는 쪽을 택합니다. 구글 검증이 필요하다고 판명되면 예비비로 유료 SERP API를 Phase 4 이후 검토합니다.

### F-05 · 수율 산술이 틀렸다 (BLOCKER · **재계산 확인**)

v1은 "15~35건/일"이라고 썼지만 자체 가정으로 계산하면:

```
하한  175 × 0.70 × 0.25 × 0.90 × 0.40 = 11.0
상한  175 × 0.80 × 0.40 × 0.90 × 0.60 = 30.2
```

**11~30건**입니다. 기본 통과를 200으로 올려도 상한 34.6건. 목표 50건을 달성하려면 기본 통과가 일 289~794건 필요합니다.

**반영:** F-01로 이메일 게이트가 검수 후단으로 이동했으므로 산식 자체가 바뀝니다. v2에서 재산출하고, **일 50건은 계약 목표가 아니라 상한값(cap)으로만 유지**합니다. 실제 처리량 SLA는 Phase 0 실측 신뢰구간으로 확정합니다.

## C. 부분 수용 — 수정해서 반영

### F-04 · SoSR 지표 (BLOCKER 지적 → 부분 수용)

**수용:** 네이버 Open API 5종은 통합검색과 다른 인덱스이고, `local`은 최대 5건인데 나머지는 100건이라 분모가 호환되지 않는다 — 사실입니다. 지표 이름과 해석을 "SERP 노출·순위·검색 점유"라고 부른 것은 잘못입니다.

**반박:** "35점 배점을 제거하라"는 처방은 과합니다. 이 배점을 없애면 "검색 결과물이 부족한 업체를 찾는다"는 제품 정의 자체가 사라집니다.

**절충 (v2 반영)**
- 지표명 변경: `SoSR` → **`ORS` (Open-API Result Share, Open API 콘텐츠 회수 점유율)**
- 채널별 분모를 고정(blog/cafe/web/news 각 상위 30, local은 제외하고 별도 boolean 신호로만 사용)
- URL 정규화 후 채널 간 중복 제거
- 브랜드 키워드와 비브랜드 키워드를 **합산하지 않고 분리 산출**
- 배점 35 → **25**로 축소, 축소분 10점은 데이터 신뢰도(+5)와 신규 축인 현장 검증 가능성(+5)에 재배분
- UI 문구에서 "검색 노출·순위·점유율" 표현 금지, "네이버 Open API 기준 콘텐츠 회수량"으로 표기

### F-02 · 네이버 API 약관 위반 가능성 (BLOCKER 지적 → **보류 · 근거 검증 실패**)

codex는 "약관 7.3② 스팸/광고 정보 작성·전송 목적 이용 금지", "검색 API 특약 2.1 검색결과 독립 노출·비왜곡" 조항을 인용했습니다. **`developers.naver.com/products/terms/` 직접 확인을 시도했으나 접근 실패했고, 검색으로도 해당 조항 번호와 문언을 독립 확인하지 못했습니다.** 따라서 조항 번호·문언은 **미검증**으로 표기합니다.

다만 **리스크 자체는 실재**합니다. 우리 시스템은 최종적으로 영업 목적 리드를 만들고, 검색 API 결과를 가공해 점수로 변환합니다.

**반영:** 사실로 확정하지 않되 **Phase -1의 필수 액션**으로 전환합니다.
1. 네이버 개발자센터 약관 전문을 직접 확보해 조항 확인
2. 애매하면 네이버에 **서면 문의**(용도: 사내 리드 발굴 분석, 결과 원문 미재배포)로 확인
3. 불허 시 대안: 업체 **공식 채널의 RSS·공개 피드 직접 확인**만으로 콘텐츠 활동량을 측정하는 축소 파이프라인 (ORS 없이 "최근 콘텐츠 활동 부족" 축만 유지)

### F-20 · 표본 크기 (HIGH 지적 → 부분 수용)

**수용:** `H0: ρ≤0.4` vs `H1: ρ=0.6`, 양측 α=.05, power=.80 검정에 약 111개가 필요하다는 계산은 맞습니다(Fisher z 변환 검산 완료: `((1.96+0.8416)/(0.6931-0.4236))² + 3 ≈ 111`). 업종별 30개는 신뢰구간이 매우 넓습니다. 회사당 다중 키워드가 독립 표본이 아니라는 지적도 맞습니다.

**반박:** "Phase 0에서 240~400개를 2인 평가로"는 비현실적입니다. 사람 라벨링 400건은 그 자체로 2주 이상이며, Phase 0의 목적(빨리 접고 갈지 판단)과 충돌합니다.

**절충 (v2 반영)**
- **Phase 0 = 탐색적 검증.** n=120, 가설검정을 하지 않고 **점추정 + 95% 신뢰구간만 보고**. 중단 기준은 "ρ 신뢰구간 상한 < 0.4" 처럼 명백한 실패에만 적용
- **Phase 4 완료 기준 = 확증 검증.** 업종별 60건 총 240건, **평가자 2인**, 검색환경 고정(비로그인·시크릿·데스크톱·지역 고정), 사전등록 `H0`, 평가자 일치도(Krippendorff α ≥ 0.67), 시간 분리 holdout
- 회사당 1개 대표 키워드만 상관분석에 사용(독립성 확보), 다중 키워드는 부차 분석

### F-25 · robots.txt 취급 (MEDIUM → 부분 수용)

**수용:** robots.txt는 법적 면허가 아니고, `noindex`는 색인 지시이지 fetch 금지가 아닙니다. v1이 둘을 동일시한 것은 부정확합니다.
**반영:** 표준 robots 파서 + 장애 시 fail-closed는 유지. `noindex`는 차단 사유가 아닌 **별도 메타데이터**로 저장. 소스별 약관·수집근거 레지스트리(`source_registry`) 신설.

### F-26 · 의료광고 (MEDIUM → 부분 수용)

**수용:** 위험 지점은 "경쟁사 비교·추천 문구가 제안서·환자 대상 광고 소재로 재사용되는 순간"입니다.
**반영:** 데이터·권한으로 **내부 분석 / 대외 제안 / 환자 대상 광고**를 3단 분리. 외부 반출에는 별도 게이트(의료기관 승인·심의 대상 판정·금지표현 검토). 시스템은 대외 문구를 생성하지 않음.

### F-28 · 일정 (MEDIUM → 부분 수용)

**수용:** 각 Phase 최소 개발일 합계만 37~46일이고, 관찰 기간·키 심사·법률 검토·수동 라벨링이 빠졌습니다. Phase 0(120건 수동 판정 + 체감 검색 평가 + 경쟁사 360건 판단)을 5~7일에 끝낸다는 가정과 Phase 6(전체 UI+RLS+E2E) 5~6일은 과소평가가 맞습니다.
**반영:** **1인 기준 12~16주**로 재계획(법률 검토·네이버 확인 대기 포함). Phase 0을 7→10일, Phase 6을 6→10일로 상향.

### F-29 · Phase -1 선행 (MEDIUM → 수용, 순서만 조정)

**수용:** 법적으로 못 쓰는 이메일 수집과 약관 미확인 네이버 API로 120건을 돌려 잘못된 골드셋을 만드는 것은 낭비라는 지적이 맞습니다.
**반영:** **Phase -1 (법무·약관·데이터원 확정)** 을 신설해 Phase 0 앞에 둡니다. 단 Phase -1은 대기 시간이 길므로(변호사·네이버 회신) 그 사이에 **법적으로 안전한 부분만** 병렬 진행합니다: 공공데이터 어댑터, U(모집단 크기) 산출, HttpClient+SSRF 방어, 홈페이지 판별(이메일 추출 없이).
