# 의사결정 기록 (Decision Log)

> 설계서의 미해결 항목에 대해 발주자가 내린 결정을 기록합니다.
> 각 결정은 **누가·언제·무엇을** 결정했는지와 **그 결정이 시스템에 미치는 영향**을 남깁니다.

## D-001 · B2B 콜드 아웃바운드 이메일의 적법성

| | |
|---|---|
| 질문 | 국내에서 사업자 공개 업무용 이메일로의 B2B 콜드 아웃바운드가 적법한가 (정보통신망법 제50조) |
| 결정 | **적법하다고 판단하고 진행** |
| 결정자 | 발주자 |
| 결정일 | 2026-07-29 |

**시스템 반영**
- `leads.contact_legal_basis` 기본값을 `pending_legal_review` → **`legitimate_interest_claimed`** 로 변경. 필드와 export 게이트는 **그대로 유지**합니다(제거하지 않음).
- `export_leads()` 의 허용 목록에 `legitimate_interest_claimed` 추가.
- `do_not_contact` · `opt_out_at` · `privacy_requests` 차단 조건은 **유지**합니다. 수신거부가 들어온 대상은 어떤 결정과도 무관하게 제외됩니다.

**남는 리스크 (기록)**
- 정보통신망법 제50조는 영리목적 광고성 정보 전송에 명시적 사전 동의를 원칙으로 하며, B2B에 대한 명문 예외 조항은 없습니다. 위반 시 과태료 대상입니다.
- 제50조의2(자동 수집 금지)는 **이 결정과 무관하게 그대로 적용**되므로, 홈페이지 이메일 자동 추출을 하지 않는 설계는 변경하지 않습니다.
- 실제 발송은 MVP 범위 밖이므로, 발송 시점에 다시 검토하는 것을 권장합니다. 이 기록이 그 근거가 됩니다.

## D-002 · 네이버 Open API 사용

| | |
|---|---|
| 질문 | 네이버 Open API를 영업 리드 발굴에 사용할 수 있는가 |
| 결정 | **사용 가능** |
| 결정자 | 발주자 |
| 결정일 | 2026-07-29 |

**시스템 반영**
- `source_registry['naver_search'].approved = true`, `written_approval_ref = 'D-002'`
- `FEATURE_ORS` 기본값 `off` → **`shadow`**
- **`on`(배점 25) 승격은 여전히 Phase 4 확증 검증(n=240) 통과가 조건입니다.** 이것은 법적 게이트가 아니라 **데이터 품질 게이트**이며, D-002로 해제되지 않습니다. 검증되지 않은 지표에 25점을 주는 것은 별개의 문제이기 때문입니다.
- fail-closed 부팅 검사 로직은 **유지**합니다. `source_registry` 를 통해 언제든 되돌릴 수 있어야 합니다.

**남는 리스크 (기록)**
- 약관 조항(7.3② 등)과 API HUB 이관 여부는 **재확인하지 못했습니다.** Phase -1 확인 항목에 그대로 둡니다.
- 네이버가 이용을 제한할 경우 `source_registry` 한 행을 `approved=false` 로 바꾸면 즉시 축소 파이프라인으로 폴백됩니다.

**재확인 (2026-07-31 · 발주자)**
- 약관 전문 확인 완료 — 스냅샷: [`docs/legal/naver-terms-2026-07-31.md`](legal/naver-terms-2026-07-31.md).
  7.3③(허용 범위 초과 저장·가공·배포 금지)·검색 API 특약 2.1(독립 노출·왜곡 금지)·8조(결과
  데이터 권리) 문언 확인. 완화 요소(본문 미저장·30일 보관·집계 중심·재배포 없음)를 인지한
  상태에서 **"사용 가능" 결정 유지**.
- **API HUB 이관 확정** (약관 부칙): 개발자센터 Search API 신규 접수 2026-07-30 24:00 중단.
  발주자는 7/30 이전 등록(기존 이용자) — **2027-06-30 까지 legacy 이용 가능.** 그 전에
  `variant: "apihub"` 이관 필요. 자격증명 실동작 확인(2026-07-31 · HTTP 200).

## D-005 · robots.txt 4xx 처리

| | |
|---|---|
| 질문 | robots.txt 가 401·403 등 4xx 를 줄 때 fail-closed 를 유지할 것인가 |
| 결정 | **허용한다** — RFC 9309 §2.3.1.3 은 400-499 를 "unavailable" 로 보고 접근 가능으로 다룰 수 있다고 하며, Google 도 같게 동작한다. **5xx·네트워크 실패는 fail-closed 유지** |
| 결정자 | 발주자 |
| 결정일 | 2026-08-05 |

**배경**: 골드셋 M2 FN 분해(2026-08-04)에서 사람은 열리는 사이트의 robots.txt 가 403
(WAF 의 봇 차단)이라 영영 판정하지 못하는 사례가 확인됐다. 이 1건 해소로 M2 재현율이
21/28 = 75% 로 기준(≥0.75)에 도달한다.

**시스템 반영**
- `robotsGate` 가 400-499 를 `unavailable_4xx` 로 기록하고 **허용**한다 (404/410 은 기존대로 `not_found`).
- 5xx·네트워크 실패·본문 절단은 그대로 fail-closed.
- 강제 위치: `robotsGate.test.ts` · `homepage.pg.test.ts` (403 사이트가 판정까지 도달).

## 결정이 바꾸지 않는 것

아래는 D-001~D-004와 무관하게 **그대로 유지**됩니다.

| 항목 | 이유 |
|---|---|
| 홈페이지 이메일 **자동 추출 금지** | 제50조의2는 별개 조항. D-001은 "전송"에 대한 결정이지 "수집 방법"에 대한 결정이 아님 |
| `do_not_contact` · `opt_out_at` · `privacy_requests` 차단 | 수신거부는 어떤 결정보다 우선함 |
| SSRF·XSS 방어 | 법적 판단과 무관한 보안 요구사항 |
| RLS·RPC 전용 쓰기 | 동일 |
| Phase 4 ORS 확증 검증 | 데이터 품질 게이트 |
| `source_registry` 승인 기반 부팅 검사 | 되돌릴 수 있어야 함 |
