# 어댑터 실 API 검증 절차

> 설계서 11장: "가짜 응답만으로 완료 처리하지 않는다."
> 이 문서는 `verifiedAgainstLiveApi` 를 `false` → `true` 로 바꾸기 위한 절차다.

## 왜 필요한가

HIRA·공정위 어댑터의 **엔드포인트 경로·응답 필드명·코드값**은 공개 문서만으로
확정할 수 없었다. data.go.kr 은 스펙을 활용신청자에게만 주는 가이드 문서와
Swagger UI 로 제공한다.

코드값이 틀리면 **수집 자체가 조용히 빗나간다** — 에러 없이 엉뚱한 업종이 수집된다.
그래서 읽어서 확인하지 않고 **호출해서 확인한다**.

### ❗ 검증 방법이 틀렸던 사례 — `dgsbjtCd=14`

2026-07-29 에는 이 코드를 "틀렸을 가능성이 높다" 고 기록했다. **코드가 아니라 방법이
틀렸다.**

처음 방법은 *코드 → 이름* 방향이었다: 코드 14 로 거른 16,987건을 표본 100건 뽑아
기관명에 '피부과' 가 몇 %인지 본다. 결과는 대조군과 같은 2.0% — 상승도 1.0배.

문제는 **피부과가 전체 의원의 45%(37,819 중 16,987)가 신고하는 과목**이라는 것이다.
표본이 통째로 희석돼 신호가 사라진다. 성형외과 의원의 45.2%도 피부과를 함께 신고한다.

방향을 뒤집으면 답이 하나다: *이름 → 코드*. "이름이 '피부과' 인 의원은 어떤 코드를
신고했는가" → 1,555곳 중 1,553곳이 14. 게다가 `totalCount` 끼리의 비교라 **표본 오차가
아예 없다.**

> **다대다 관계에서는 희소한 쪽에서 물어야 한다.**
> `pnpm spike verify` 는 이제 이 방향을 1급 방법으로 쓰고, 이름 필터를 지원하지 않는
> API 에서만 상승도 휴리스틱으로 폴백한다.

### 📄 가이드 문서 확보 (2026-07-30)

`OpenAPI활용가이드_건강보험심사평가원(병원정보서비스)_210616.docx` 를 받아 스펙을 대조했다.
실측으로 알아낸 것이 문서와 **전부 일치**한다.

| 항목 | 문서 | 우리 코드 |
|---|---|---|
| `dgsbjtCd` 14 | 피부과 | ✅ `dgsbjt_derm` |
| `dgsbjtCd` 08 | 성형외과 | ✅ `dgsbjt_plastic` |
| `clCd` 31 / 51 / 41 | 의원 / 치과의원 / 치과병원 | ✅ |
| `yadmNm` | 병원명 (UTF-8 인코딩 필요) | ✅ `scope=name` 이 쓰는 파라미터 |

전체 코드표를 `HIRA_DGSBJT_NAMES`(43종)·`HIRA_CL_NAMES`(15종)로 옮겨 두었다.
업종을 늘릴 때 여기서 고른다 (안과 12, 한의원은 종별 93 등).

**두 가지를 고쳤다.**

1. 코드 탐색 범위가 `00~30` 이었다. 문서의 표는 치과(50~61)·한방(80~85)까지 있으므로
   그 범위로는 치과 계열 코드를 **구조적으로 찾을 수 없었다.** 이제 문서화된 코드표를
   후보 집합으로 쓴다.
2. 가이드는 `hospInfoService1/getHospBasisList1`(2021년판)을 적지만 우리는 `v2` 를 쓴다.
   실키에서 v2 가 정상 응답하고 필드도 같아 그대로 둔다 — v2 가 죽으면 후보 탐색이
   v1 로 넘어가 알려준다.

### ❗ 공정위 — 경로 추측은 무의미하다

일부러 만든 존재하지 않는 경로(`1130000/NoSuchServiceXYZ/getNothing`)가 후보들과
**완전히 같은 `500 Unexpected errors`** 를 돌려준다. 즉 이 응답으로는

- 경로가 틀렸는지
- 이 데이터셋을 활용신청하지 않았는지
- 서비스가 죽었는지

를 **구분할 수 없다.** 후보를 더 넣어 두드려 봐야 같은 답만 나온다.
`verify` 가 이제 음성 대조군을 함께 찍어 이 사실을 보고한다.

**필요한 것:** **공정거래위원회 가맹정보** 데이터셋의 가이드 문서. HIRA 가이드에는
공정위 정보가 없다 (확인함 — `공정거래|가맹|브랜드|1130000` 검색 결과 0건).

받는 곳: data.go.kr → 마이페이지 → 오픈API → 활용신청 현황 →
해당 데이터셋(15125467 브랜드 목록 / 15110241 브랜드별 가맹점 현황) →
**참고문서** 또는 **상세설명** 의 요청주소.

그 화면에서 **승인 상태**도 함께 확인해야 한다. `500 Unexpected errors` 는
미승인일 때도 같은 응답이므로, 신청 자체가 안 돼 있으면 주소를 고쳐도 소용없다.

### 발주자 결정 (2026-07-30): `name` — 기관명 기준

`settings.collection.hira_scope = 'name'`. 기관명에 과목명이 든 의원만 모은다.

| | 피부과 | 성형외과 | 치과 | 합계 |
|---|---:|---:|---:|---:|
| `name` (현재) | 1,555 | 1,236 | 19,399 | **22,190** |
| `specialty` | 16,987 | 4,883 | 19,399 | 41,268 |

근거: 피부과 신고는 전체 의원의 45%가 하고 있어 `specialty` 로 모으면 "피부과 마케팅"
제안이 맞지 않는 일반의원이 대량 섞인다. 실측 표본 16곳은 100% 기관명에 과목명이 있다.

**되돌리는 방법:** `update settings set value = jsonb_set(value, '{hira_scope}', '"specialty"')
where key = 'collection';` — 코드 배포가 필요 없다. 좁힌 뒤 소진이 너무 빠르면 넓히는 것이
유일한 대응이므로, 그때 배포를 기다리게 만들지 않는다.

이름 키워드는 과목명 그대로 쓴다. 실측: `피부` 로 넓히면 +4곳, `성형` 은 +1곳뿐이라
짧은 키워드는 오탐 위험만 늘린다. 이름에 두 과목이 다 든 의원은 2곳
(`미피부과성형외과의원`·`안성열성형외과피부과의원`)이라 업종 간 중복은 무시할 수준이다.

> ⚠️ **업종 구성 쏠림**: 치과 87.4% / 피부과+성형외과 12.6%(2,791곳).
> 업종 비율 상한 60%를 지키려면 리드의 40%를 2,791곳에서 뽑아야 하므로 이쪽이 약 3개월 만에
> 먼저 소진된다. 그 뒤 일 승인 상한이 50 → 30 으로 낮아진다. 결론 E 의 현실적 산출량
> (7~21건/일)에서는 구속력이 없지만, 목표를 올릴 때 먼저 부딪히는 벽이다.

## 1단계 — 키 발급

1. [data.go.kr](https://www.data.go.kr) 회원가입
2. 아래 데이터셋에 **활용신청** (자동승인, 보통 몇 분~2시간)
   - [건강보험심사평가원_병원정보서비스](https://www.data.go.kr/data/15001698/openapi.do) (15001698)
   - [공정거래위원회_가맹정보_브랜드 목록](https://www.data.go.kr/data/15125467/openapi.do) (15125467)
   - [공정거래위원회_가맹정보_브랜드별 가맹점 현황](https://www.data.go.kr/data/15110241/openapi.do) (15110241)
   - [국세청_사업자등록정보 진위확인 및 상태조회](https://www.data.go.kr/data/15081808/openapi.do) (15081808)
3. 마이페이지 → 오픈API → 인증키에서 **일반 인증키(Decoding)** 복사

> ❗ **Encoding 키가 아니라 Decoding 키**를 넣어야 한다.
> Encoding 키를 넣으면 이중 인코딩되어 `SERVICE_KEY_IS_NOT_REGISTERED_ERROR` 가 난다.

4. 활용신청 상세 화면에서 **가이드 문서(.docx/.hwp)** 를 내려받아 둔다.
   엔드포인트가 우리 후보와 다르면 그 문서의 "요청주소" 를 쓴다.

## 2단계 — 검증 실행

```bash
# .env
FEATURE_SOURCE=live
DATA_GO_KR_SERVICE_KEY=<Decoding 키>
```

```bash
pnpm spike verify
```

이 명령은:
1. 엔드포인트 후보를 순서대로 두드려 **실제로 응답하는 것**을 찾는다
2. 응답 필드가 `HiraHospitalItem` / `FtcBrandItem` 매핑과 맞는지 확인한다
3. **코드값을 경험적으로 검사한다** — `dgsbjtCd=14` 가 피부과라면 반환된 기관명
   대부분에 "피부과" 가 들어 있어야 한다
4. 실제 응답을 `fixtures/http/` 에 녹화한다

### 코드값 검사를 어떻게 읽는가

> **이것은 증명이 아니라 신호다.**
> 코드가 맞으면 보통 80% 이상, 틀리면 5% 미만으로 갈린다. 임계값은 50%다.
> 50~80% 구간이 나오면 표본을 늘려(`numOfRows`) 다시 보거나 사람이 직접 확인한다.

### 상태 코드 읽는 법

| HTTP | 뜻 |
|---|---|
| 401 | **경로는 맞다.** 키가 거부됨 → Decoding 키인지 확인 |
| 403 | 활용신청 승인 대기 중이거나 트래픽 한도 초과 |
| 404 | 경로 없음 |
| 500 | 대개 **미등록 서비스** — 경로가 틀렸거나 이 데이터셋을 활용신청하지 않음 |

## 3단계 — 결과 반영

### 통과한 경우

1. `hira.ts` / `ftc.ts` 의 `verifiedAgainstLiveApi = true`
2. `fixtures/http/*.json` 을 커밋 (`.gitignore` 에서 제외 해제)
3. 녹화된 fixture 로 매핑 회귀 테스트 추가
4. `pnpm spike universe` 로 실제 모집단 `U` 측정 → 소진 곡선 산출

### 실패한 경우

리포트가 알려주는 대로 고친다.

| 진단 | 조치 |
|---|---|
| 다른 후보가 동작 (warn) | `hira.ts` 의 `ENDPOINT` / `ftc.ts` 의 `ENDPOINTS` 를 그 값으로 |
| 필드명 불일치 | `HiraHospitalItem` / `FtcBrandItem` 을 관찰된 키에 맞춤 |
| 코드값 비율 낮음 | `HIRA_CODES` 수정 후 재실행 |
| 전 후보 500 | 가이드 문서의 요청주소를 후보 목록에 추가 |

**`verifiedAgainstLiveApi` 는 통과할 때까지 `false` 로 둔다.** 그래야 스파이크와
워커가 계속 경고한다. 이 플래그를 미리 켜는 것은 "가짜 응답으로 완료 처리"와 같다.
