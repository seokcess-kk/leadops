## B. 수용 → 수정 완료

### C-06 · NAT64 프리픽스를 4바이트만 검사 (MEDIUM → 실제 우회)

`64:ff9b:dead:beef::7f00:1` 이 `nat64:loopback` 으로 오분류되고, 테스트 정책의
loopback 완화가 `reason.endsWith(":loopback")` 문자열 비교였기 때문에 통과했습니다.

**수정 3가지**
1. NAT64 프리픽스를 **12바이트 전부** 검사 (`ip.ts`)
2. 정책 완화 판단을 문자열이 아니라 **실제 주소**로 (`isLoopbackAddress()`)
3. **추가 발견** — 위 둘을 고치자 이번엔 그 주소가 *어느 차단 목록에도 없어* 통과했습니다.
   차단 목록(deny-list)만으로는 비할당 IPv6 를 걸러낼 수 없습니다.
   → **IPv6 를 기본 거부로 전환**: 전역 유니캐스트 `2000::/3` 밖은 전부 차단.

> 이 3번이 이번 리뷰에서 가장 값진 발견입니다. codex 의 지적을 고치는 과정에서
> 원래 지적보다 큰 설계 결함(deny-list 접근 자체)이 드러났습니다.

### C-03 · 크기 상한이 스트림을 끊지 않음 (HIGH)

상한 이후 chunk 를 버리기만 하고 EOF 까지 계속 해제해서, 압축 폭탄이 CPU·대역폭을
그대로 태웠습니다. → 상한 도달 즉시 `res.destroy()` + `decompressor.destroy()`.
의도된 절단은 정상 결과(`truncated: true`)로 처리합니다.
**테스트**: 40MB 를 흘려보내는 서버에 8KB 상한 → 전송 완료 전에 끊김을 검증.

### C-04 · serviceKey 가 로그·에러에 노출 (HIGH)

공공데이터포털 키가 쿼리스트링에 있는데 그 URL 이 그대로 재시도 경고·예외 메시지·
`hops` 에 실렸습니다. → `redactUrl()` 신설(민감 쿼리 파라미터 + userinfo 마스킹),
`client.ts` 의 모든 로그·에러 경로와 `dataGoKr.ts` 의 에러 컨텍스트에 적용.

### C-05 · robots 패턴 ReDoS (HIGH)

원격 robots.txt 의 `*` 가 중첩 `.*` 로 변환되어 백트래킹 폭발이 가능했습니다.
→ 연속 와일드카드 접기, 와일드카드 12개·패턴 512자 상한(초과 시 규칙 무시), 컴파일 캐시.
**테스트**: `*a` × 40 패턴에 4,000자 경로를 넣어 300ms 이내 종료 검증.

### C-08 · crawl-delay 를 다른 키로 조회 (MEDIUM)

그룹은 접두 일치로 고르는데(`leadopsbot`) delay 는 전체 UA 토큰(`leadopsbot/1.0`)으로
찾아서, `User-agent: LeadOpsBot` + `Crawl-delay: 7` 이 적용되지 않았습니다.
→ `selectGroup()` 이 매칭된 agent 키를 함께 반환하고 그 키로 delay 조회.

### C-10 · NODE_ENV 누락 시 mock 이 조용히 부팅 (MEDIUM)

기본값이 `development` + `mock` 이라, `NODE_ENV` 없이 배포하면 목업이 돕니다.
→ `MockSourceAdapter` 생성자가 `NODE_ENV=production` 이면 던지도록 2차 방어선 추가.

### C-11 · 손상된 포털 응답이 fail-open (LOW → 실질 HIGH)

`header` 나 `body` 가 없어도 빈 결과로 넘겼습니다. 포털 장애가 **"이 업종에 업체 0개"**
로 둔갑하는데, 이는 수집 파이프라인에서 가장 나쁜 실패 방식입니다.
→ `resultCode === "00"` 과 객체 `body` 를 요구. 정상적인 0건(`items: ""`)과는 구분.

기존 테스트 "body 자체가 없어도 죽지 않는다"는 **이 고장을 정상으로 굳히고 있었으므로
삭제**하고, 반대 방향 테스트로 교체했습니다.

### C-09(일부) · 국제 전화번호 · assertNoPII 검사 범위 (MEDIUM)

`+82-10-1234-5678` 이 마스킹되지 않았고 `assertNoPII` 가 전화번호를 검사하지 않았습니다.
→ 국제 표기 정규식 추가, `assertNoPII` 가 email·rrn·phone·intl_phone 을 모두 검사,
정규식 인스턴스를 매번 새로 만들어 `lastIndex` 상태 공유 제거.

## C. 부분 수용 — 한계를 문서화

### C-09(나머지) · 사람 이름은 마스킹되지 않는다

**수용하지만 정규식으로 풀 수 없습니다.** "김민수"를 이름으로 식별하는 신뢰할 만한
패턴은 없습니다. codex 의 제안(경계 DTO 허용 필드 방식)이 옳은 해법입니다.

**반영**: `REDACTION_LIMITS` 상수로 **무엇을 못 잡는지**를 코드에 명시했습니다.
- 로그: `redactPII` 가 1차 방어선 (키 이름 휴리스틱 + 패턴)
- LLM 경계: **허용 필드 DTO 가 1차 통제**, `redactPII` 는 2차 방어선 — Phase 5 구현 항목

"못 잡는 것을 잡는 척"하지 않는 것이 이 단계에서 할 수 있는 최선입니다.

## D. 이미 반영되어 있던 것

### C-12 · SSRF 기본 정책 테스트가 동어반복

임의 포트 loopback 을 쓰면 포트 검사에서 먼저 걸려 IP 판정 경로를 검증하지 못한다는
지적은 맞습니다. **다만 codex 가 본 스냅샷 이후 이미 보완되어 있었습니다** —
`포트가 허용 범위라도 loopback IP 자체를 차단한다`(포트 80)와
`클라우드 메타데이터 주소를 차단한다` 테스트가 IP 경로를 단독 검증합니다.

이번에 추가로 보강한 것: 테스트 정책 완화 범위 검증(loopback 만 열리고 사설·NAT64 위장은
막힘), Map/Set/TypedArray/getter redaction, 압축 스트림 조기 종료.
